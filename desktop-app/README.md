# Yousoro Workspace Desktop

Установщик един для всех аккаунтов. В веб-кабинете откройте «Компьютер» → «Код активации лаунчера» и вставьте код в приложении. Keychain или Windows Credential Manager хранит выданный ключ ПК. Аккаунту доступны два места для ПК. Мобильные профили учитываются отдельно.

Маршрут запускается после выдачи лицензии, оплаты обслуживания и применения региона. Лаунчер сверяет статус каждые 15 секунд, а во время применения региона — каждые 3 секунды. Кнопка «Я оплатил — проверить сейчас» запрашивает статус сразу. Подробнее об API и миграции см. [Лицензирование Desktop](../docs/desktop-licensing.md).

## Рабочий браузер и десктопные клиенты

- Chrome, Brave или Edge открывается с отдельным каталогом `profiles/<region_code>` для активного узла. Единственный локальный SOCKS5 передаётся аргументом запуска. Рабочий профиль отключает QUIC, встроенный DoH и спекулятивное разрешение имён. SOCKS5 передаёт имена удалённой стороне. Лаунчер задаёт локаль узла, отключает предзагрузку, встроенный DoH, автоперевод и автозаполнение профиля и платёжных полей. Когда у узла нет локали, настройка приложения задаёт английский вариант по умолчанию. Рабочая вкладка перед переходом на сайт измеряет Intl timezone и список языков. Несовпадение оставляет пользователя на локальной странице проверки. На Windows для профиля с другой зоной лаунчер открывает порт CDP на loopback и применяет зону до открытия рабочей страницы. Если контроллер не может запуститься, лаунчер показывает подсказку о часовой зоне и оставляет рабочую страницу закрытой.
- Перед запуском закрытого профиля лаунчер применяет значения геолокации и WebRTC, сохраняя остальные поля Chromium Preferences. Для сброса откройте «Рабочее место», закройте браузер нужного региона и подтвердите «Очистить профиль». Очистка удаляет cookies, историю и прочие локальные данные этого профиля.
- На Windows Workspace проверяет процессы, MSIX, стандартные установки и записи удаления Claude. Классические клиенты получают параметры локального прокси при запуске. Для совместимых Store-пакетов предпочтителен запуск исполняемого файла. Если нужен AppsFolder, пользователь может вручную включить точечный PAC. Он меняет только AutoConfigURL, сохраняет настройки перед записью и восстанавливает их при отключении, выходе или следующем старте. При уже настроенном системном прокси или PAC Workspace отказывается заменять его.
- Killswitch включается при каждом подключении. Прокси Workspace держит один локальный порт на весь сеанс маршрута. Лаунчер проверяет процесс Xray и наблюдаемый IPv4 через Relay. Первый или изменившийся IP дополнительно сравнивается с выходом назначенного шлюза через API диагностики. Если проверка не прошла, прокси закрывает текущие TCP-потоки и отклоняет новые. Следующие попытки выполняются с задержкой до 30 секунд. После восстановления открытые приложения могут снова использовать тот же порт.
- Область защиты включает рабочий браузер и соединения приложений, которые используют прокси Workspace. Windows PAC применяется к целевым HTTP(S)-доменам совместимых клиентов. При сбое Xray он остаётся установлен, при штатном завершении восстанавливается, а после аварии лаунчера журнал обрабатывается при следующем старте. Windows-клиент может обойти не загружаемый PAC. На macOS используются параметры запуска и переменные окружения. Управление прямыми сокетами произвольных приложений потребует системного сетевого фильтра.
- Выключатель Killswitch отключает проверку Relay для текущего сеанса. Параметры явного прокси остаются в силе, а Xray по-прежнему перезапускается при обнаружении гибели процесса. После штатного отключения обычные приложения используют свои сетевые настройки. Заново откройте рабочий браузер и терминал, если подключили новый маршрут на другом порту.
- Workspace показывает последний список установленных клиентов сразу после проверки локального кэша. Пакеты Windows читаются из реестра текущего пользователя, а процессы проверяются отдельно через Win32. Нажмите «Обновить список приложений», если только что установили клиент. Если клиент остаётся в фоне после закрытия окна, завершите его через меню клиента и повторите перезапуск.
- Радар запрашивает публичный IPv4 через локальный SOCKS у выделенного адреса диагностики Workspace. Задержка измеряется запросом HTTPS. Геолокацию и репутацию выхода возвращает кэшированная сводка API. Проверка ПК записывает внешний IPv4 для сверки с мобильным Радаром за последние 30 минут. Быстрая проверка читает настройки профиля. «Проверить в браузере» открывает страницу Workspace и возвращает одноразовый отчёт по выходному адресу, локали, разрешению геолокации и ICE. DNS через bash.ws и внешний WebRTC через Cloudflare STUN включены по умолчанию для ручной проверки. Их можно отключить в технических подробностях. Отдельная кнопка на странице проверяет камеру и микрофон локально. Быстрая проверка не измеряет IPv6. Если для браузерной пробы настроен адрес IPv6-only, публичный IPv6 считается признаком утечки. Если адрес внешней пробы отсутствует, Радар показывает действующее локальное правило активного профиля. Внешняя проба без результата остаётся непроверенной. Закрытый профиль оставляет обязательные проверки браузера незавершёнными. Сверка со смартфоном нужна для сопоставления адресов устройств и отмечается отдельно. Если базовые проверки прошли, Радар показывает готовность даже без необязательных внешних проб. HTTP 403/429 показываются как ограничение сервиса. Статус WebRTC отражает конфигурацию, поведение сети стороннего приложения зависит от того, учитывает ли оно настройки прокси.

Фоновая проверка процессов Claude, ChatGPT и Cursor выполняется примерно каждые две секунды. Приложение предупреждает о запуске без аргументов рабочего порта или при выключенном маршруте. Безопасный перезапуск закрывает только экземпляры из обнаруженного пути и запускает их с параметрами прокси. При недоступном пути или запуске из другого каталога потребуется штатно закрыть клиент. Системное уведомление зависит от настроек ОС и регистрации приложения.

Кнопка «Скопировать диагностику» в подвале лаунчера сохраняет в буфер обмена JSON со статусом текущего маршрута, семью результатами Радара, состоянием Process Guard, выбранным и активным движками и итогом восстановления TUN. Последние 25 событий Xray, sing-box и watchdog берутся из журнала текущего сеанса. В выгрузку попадают заранее заданные сообщения событий и статусы. Сырые логи ядра, адреса и данные профиля для экспорта не читаются.

## Split-TUN и Proxy

В разделе «Рабочее место» можно выбрать «Весь ПК (Split-TUN)» для поддерживаемых сервисов или «Только браузер (Proxy)» для рабочего профиля и явно подключённых клиентов. Фактический движок указан рядом со статусом маршрута. Лаунчер сохраняет выбор в каталоге данных. Для действующих установок исходный режим — Proxy. Если пользователь отменит запрос прав, файлы sing-box/Wintun не пройдут проверку или адаптер не запустится, лаунчер подключит Xray и покажет причину. Для смены режима сначала отключите маршрут.

Системный вход Split-TUN применяет маршрутизацию v3. Целевые домены идут к Relay, для целевых DNS-запросов A используется FakeIP. Остальные типы запросов к этим доменам, IPv6 и UDP для целевых соединений отклоняются. Обычный системный трафик идёт напрямую. Транспорт к адресу и порту самого Relay обрабатывается до анализа TLS. Рабочий браузер, CLI и Радар используют стабильный loopback SOCKS5/HTTP CONNECT с доступом только к Relay. Поддерживаемые приложения могут пользоваться системным маршрутом, пока TUN и Relay здоровы.

Подтверждение UAC на Windows или прав администратора на macOS требуется при создании адаптера. Привилегированный sing-box получает конфигурацию через stdin. Параметры доступа к Relay получает отдельный непривилегированный sing-box. При Dedicated Pass HOLD локальный шлюз закрывает существующие потоки, отклоняет новые и останавливает Relay. Системный адаптер продолжает маршрутизировать обычный интернет. Восстановление с тем же Relay использует тот же адаптер. Если Relay изменился или Split-TUN был запущен уже в HOLD, для возобновления требуется переподключение.

При остановке, закрытии окна или выходе из лаунчера supervisor останавливает системный sing-box. При аварийном завершении лаунчера закрытие управляющего сокета также запускает очистку. На следующем запуске лаунчер проверяет журнал сессии и освобождение адаптера. Если очистка не подтверждается, повторный старт Split-TUN ограничивается до устранения проблемы. При потере адаптера watchdog закрывает рабочие соединения и переводит маршрут в ошибку. Для нового старта отключите маршрут и подключитесь снова. При временной потере Relay watchdog повторяет проверку и запускает Relay с задержкой.

Рабочий профиль использует `auto_route` без `strict_route`, поскольку в Windows sing-box 1.12.22 включает WFP при `strict_route`. Если системный интерфейс исчезнет, ОС может восстановить прямую маршрутизацию до обработки события лаунчером. Windows DNS через другие интерфейсы и трафик без распознанного имени тоже могут идти напрямую. [Реализация настройки strict_route в sing-tun](https://github.com/SagerNet/sing-tun/blob/v0.7.11/tun_windows.go#L177-L187).

Для проверки эталонных профилей и живого loopback задайте `SING_BOX_TEST_BIN` с путём к sing-box 1.12.22 и запустите `python -m pytest backend/test_launcher_archives.py -k desktop_split_tun` из корня. Rust-тесты с этой переменной также проверяют фактические профили системного входа и Relay и соединение через локальный тестовый Relay. Тесты используют синтетические данные.

Нативный регрессионный тест запускается на Windows командой `cargo test --manifest-path src-tauri/Cargo.toml real_windows_chromium -- --nocapture` из каталога `desktop-app`. Перед запуском задайте `WORKSPACE_CHROMIUM_TEST_BIN` с путём к Chrome. Два временных профиля открывают локальные тестовые страницы. Тест сравнивает исходную зону ОС с рабочей страницей, новой вкладкой, кросс-сайтовым iframe и dedicated worker.

## Разработка

Нужны Node.js 22, Rust stable, Python 3 и системные зависимости Tauri. Из каталога `desktop-app` выполните `npm ci`. Задайте переменную окружения `XRAY_RELEASE_TAG` с опубликованным тегом XTLS/Xray-core, затем выполните:

```sh
python scripts/prepare_xray.py
python scripts/prepare_sing_box.py
npm run build
cargo test --manifest-path src-tauri/Cargo.toml
npm run tauri -- dev
```

Подготовщик проверяет SHA-256 архивов из выбранного релиза и раскладывает исполняемые файлы для `binaries/xray` в `bundle.externalBin`:

| Цель | Файл относительно `src-tauri/` |
| --- | --- |
| Windows x64 | `binaries/xray-x86_64-pc-windows-msvc.exe` |
| macOS Apple Silicon | `binaries/xray-aarch64-apple-darwin` |
| macOS Intel | `binaries/xray-x86_64-apple-darwin` |
| macOS Universal | `binaries/xray-universal-apple-darwin`, объединённый через `lipo` |

Tauri размещает `xray.exe` или `xray` рядом с исполняемым файлом приложения. Workspace проверяет контрольную сумму Windows и локальных macOS-сборок, а в пакете `.app` проверяет подпись Xray. Туннель слушает только loopback и получает конфигурацию через stdin.

Подготовщик sing-box проверяет закреплённые SHA-256 архивов версии 1.12.22 и Wintun 0.14.1. На Windows он записывает `binaries/sing-box-x86_64-pc-windows-msvc.exe` и `binaries/wintun.dll`. NSIS устанавливает `sing-box.exe` и `wintun.dll` рядом с лаунчером. На macOS скрипт подготавливает обе архитектуры и собирает `binaries/sing-box-universal-apple-darwin` через `lipo`. Файлы лицензий устанавливаются в ресурсы приложения.

Для локальной Windows-сборки из `desktop-app` после подготовки обоих sidecar создайте файл `../.scratch/desktop-local-bundle.json` с содержимым `{"bundle":{"createUpdaterArtifacts":false}}` и выполните:

```sh
npm run tauri -- build --bundles nsis --config ../.scratch/desktop-local-bundle.json
```

На macOS установите обе цели Rust командой `rustup target add aarch64-apple-darwin x86_64-apple-darwin` и выполните `npm run tauri -- build --target universal-apple-darwin --bundles app,dmg --config ../.scratch/desktop-local-bundle.json`.

## Релиз

Запустите workflow **Desktop release** с опубликованным тегом Xray. Он готовит Xray, sing-box и Wintun для соответствующих платформ, проверяет сборку React и тесты Rust, собирает Windows x64 NSIS и macOS Universal DMG и выгружает установщики в артефакты запуска. Для подписанного дистрибутива задайте шесть секретов GitHub Actions.

- `APPLE_CERTIFICATE` — контейнер Developer ID Application `.p12` в Base64.
- `APPLE_CERTIFICATE_PASSWORD` — пароль контейнера.
- `APPLE_SIGNING_IDENTITY` — полное имя Developer ID Application из сертификата.
- `APPLE_ID` и `APPLE_PASSWORD` — email Apple Account и пароль приложения.
- `APPLE_TEAM_ID` — Team ID команды Apple Developer.

Workflow импортирует сертификат во временный Keychain macOS-раннера и проверяет доступ к ключу пробной подписью. Tauri подписывает приложение и DMG. Отдельные шаги отправляют образ в Apple, прикрепляют билет и проверяют его перед выгрузкой. Ожидание Apple ограничено 45 минутами, задание macOS — 60 минутами, задание Windows — 35 минутами. Для macOS нужны все шесть секретов.

## Обновления из приложения

Первая установка сборки с updater выполняется установщиком. Проверка запускается через две секунды после открытия окна, независимо от восстановления аккаунта, и повторяется каждые четыре часа. При сетевой ошибке стартовая проверка повторяется через 15 секунд и затем через минуту. Её можно отключить или запустить вручную в разделе «Устройства и настройки». Перед установкой приложение отключает туннель и восстанавливает управляемый системный прокси.

Workflow подписывает файлы ключом Tauri и публикует релиз `desktop-v<версия>` с Windows NSIS, нотарифицированным macOS DMG, архивом `.app.tar.gz`, подписями и `latest.json`. Публикация начинается после успешной сборки обеих платформ. Перед каждым новым релизом увеличьте `version` в `src-tauri/tauri.conf.json` и заполните `release_notes` при запуске workflow.

Секреты GitHub Actions `TAURI_SIGNING_PRIVATE_KEY` и `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` используются только на раннерах. Публичный ключ находится в `tauri.conf.json`. Храните резервную копию приватного ключа и пароля вне репозитория. Для первоначальной настройки новой независимой цепочки подписи используется `npm run tauri -- signer generate --write-keys <путь-вне-репозитория>`.

Workflow публикует релизы только в `MartiAble/YousoroWorkspace-app`, из ветки `main`. Переменная `DESKTOP_UPDATE_BASE_URL` указывает на [каталог публичных релизов](https://github.com/MartiAble/YousoroWorkspace-app/releases/latest/download). Клиент проверяет `latest.json` по этому адресу, а манифест ссылается на файлы конкретного тега, чтобы смена текущего релиза не нарушала скачивание уже выбранной версии.

Обычный API и выделенный адрес диагностики задаются файлами `src-tauri/config/api-origin.txt` и `src-tauri/config/diagnostics-origin.txt`. При необходимости их можно переопределить переменными сборки `DESKTOP_API_ORIGIN` и `DESKTOP_DIAGNOSTICS_ORIGIN`. Оба значения должны быть HTTPS-origin без пути и учётных данных.

Для доставки обновлений через `workspace.yousoro-projects.ru` можно отдельно настроить HTTPS-зеркало каталога `/updates/` и задать `DESKTOP_UPDATE_BASE_URL=https://workspace.yousoro-projects.ru/updates` в сборках этого канала. Зеркало должно отдавать `/updates/latest.json` и подписанные файлы, на которые ссылается манифест. Сначала загрузите файлы версий и подписи, затем замените `latest.json`. Установленные клиенты начинают обращаться к новому адресу после получения сборки с этим адресом.

Радар сверяет текущую привязку ПК с активными слотами из `/api/me`, а телефоны показывает по зарегистрированным iOS/Android-привязкам. Ручная проверка в браузере по умолчанию использует bash.ws для сравнения DNS. Она сравнивает резолверы системного и SOCKS5-маршрутов на тестовых именах. При блокировке тестового домена узлом результат остаётся неопределённым. Разные резолверы в пробе не подтверждают поведение всех приложений.
